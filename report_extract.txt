Abstract

MediScan is a full-stack, role-based digital healthcare web application developed as
the primary artefact for this final year project. The system addresses the fragmented
nature of outpatient digital care by combining patient triage, verified doctor discovery,
structured appointment management, AI-assisted symptom analysis, care plan
publishing, booking confirmation payment handling, simple medicine inventory
tracking, and a multi-role notification infrastructure into a single integrated platform.
The system serves three principal user roles -- patient, doctor, and superadmin --
each with a dedicated dashboard and a distinct set of permitted operations.

The backend is implemented as a modular monolith REST API built with Node.js and
Express, organized into feature modules covering authentication, user governance,
appointments, symptom analysis, care plans, notifications, and system monitoring.
Data has persisted in MongoDB through Mongoose schemas. The frontend is a React
single-page application using React Router for role-based route separation, Tailwind
CSS for styling, and Radix UI primitives for accessible modal interactions.
Authentication is handled via JSON Web Tokens stored in HTTP Only cookies, with
Google OAuth support for social sign-in. The system also integrates with the Google
Calendar API for doctor schedule synchronization and with the Mistral AI chat
completion API for the symptom checker module.

The AI-assisted symptom checker represents the most technically distinctive
component of the system. It accepts patient-submitted symptoms, duration, severity,
and relief factors, constructs a structured clinical prompt, and submits it to the Mistral
large language model via a chat completion API call. The model returns a structured
assessment including urgency classification, possible conditions, care
recommendations, and escalation advice. A rule-based fallback mechanism is
implemented to maintain service continuity when the AI provider is unavailable. This
use of a large language model for natural language symptom triage situates MediScan
within the broader field of AI-assisted clinical decision support.

The academic question explored in this project is: to what extent does AI-assisted
symptom triage improve early healthcare decision support compared to manual self-
assessment symptoms? The project was developed following an incremental Agile

demonstrable module before the next was begun. The report presents the full system

integration, insecure configuration defaults, and base64-based file uploads, all of
which are discussed as areas for future improvement.

1. Introduction

1.1 Project Briefing

1.1.1 Overall Working, Problem Domain, and Technical Solution
The delivery of outpatient healthcare presents a coordination challenge that spans
multiple stakeholders -- patients seeking timely medical attention, doctors managing
complex appointment schedules and clinical records, and administrators ensuring
platform quality and trust. In the absence of integrated digital tooling, these
stakeholders typically operate through disconnected channels: patients discover
doctors through word of mouth or informal directories, appointments are booked via
phone, consultation records are maintained in paper files or separate electronic
systems, and symptom self-assessment is conducted through general search engines
with no personalized clinical guidance. This fragmentation reduces efficiency,
increases the risk of miscommunication, and limits continuity of care.

MediScan was designed and developed to address these challenges within a single,
integrated healthcare web platform. The system enables patients to discover verified
doctors through a searchable public directory, check real-time availability, book
appointments with optional document uploads, receive consultation summaries and
prescriptions, use an AI-assisted symptom checker for preliminary triage, browse and
request structured care plans, complete booking confirmation payments, and stay
informed through a real-time notification inbox. Doctors can manage their appointment
queues, record detailed consultation outcomes including diagnoses, prescriptions,
scan requests, and follow-up plans, view comprehensive patient record timelines, and
coordinate their schedules through configurable availability settings with optional
Google Calendar synchronization. Superadmins govern the platform by verifying
doctor credentials, managing user account status, publishing care plans, reviewing
medicine inventory, and maintaining overall data quality.

Technically, MediScan is implemented as a npm workspace monorepo containing two
primary applications. The backend is a Node.js and Express REST API organized into
feature modules under the modules directory, covering authentication, user
management, symptom analysis, appointments, care plans, notifications, and system
monitoring. Data has persisted in MongoDB through Mongoose document models.
The frontend is a React single-page application using React Router v6 for public,

                                                       10
patient, doctor, and admin route separation, Tailwind CSS for utility-first styling, and
Radix UI primitives for accessible dialog components. Authentication uses JWT tokens
stored in HTTP Only cookies with role-based middleware enforcing access control at
both the API and frontend route levels. External integrations include Google OAuth for
social sign-in, the Google Calendar API for doctor schedule events, an SMTP email

The system was developed incrementally, with each feature module implemented as
a complete vertical slice -- backend model, service, controller, routes, and frontend

continuously deployable and demonstrable state throughout development and directly
reflects the iterative Agile methodology described in Section 3.

1.2 AI Implementation

1.2.1 AI Aspect Addressed
MediScan implements Artificial Intelligence through its symptom checker module,
which uses the Mistral large language model via a chat completion API to perform AI-
assisted clinical symptom triage. The AI aspect being addressed is Natural Language
Processing (NLP). Specifically, the system leverages the natural language
understanding and generation capabilities of a large language model to interpret a
patient-submitted symptom profile -- including symptom names, duration, severity,
and relief factors -- and produce a structured clinical assessment in natural language
output that is subsequently parsed into a structured JSON format.

NLP is the branch of artificial intelligence concerned with enabling computers to
understand, interpret, and generate human language in a meaningful way (Devlin et
al., 2019). The Mistral model used in MediScan is a transformer-based large language
model trained on large corpora of text, which gives it the capacity to reason about
medical symptom descriptions expressed in natural language and to generate
contextually appropriate clinical guidance. The system does not use computer vision,
robotics, or classical machine learning pipelines such as decision trees or neural
network classifiers trained on bespoke datasets. The intelligence of the system derives
entirely from the pre-trained language model accessed through the Mistral API.

1.2.2 Learning Type -- Supervised Learning Justification
The AI capability used in MediScan is based on supervised learning, and more
specifically on the supervised pre-training and instruction fine-tuning paradigm used
to train large language models such as Mistral. In supervised learning, a model is
trained on labelled input-output pairs such that it learns to map inputs to correct outputs
based on the labels provided during training (Goodfellow, Bengio and Courville, 2016).
Mistral's underlying models are trained on vast text corpora using next-token
prediction, which is a form of self-supervised learning closely related to supervised
learning in that the labels are derived from the data itself. The models are subsequently
fine-tuned using Reinforcement Learning from Human Feedback (RLHF) and
instruction-following supervision, which are forms of supervised learning in which
human-annotated responses serve as training labels (Ouyang et al., 2022).

                                                       12
The justification for classifying MediScan's AI as supervised-learning-based rests on
the fact that the model's ability to follow structured instructions, produce formatted
JSON output from a natural language prompt, classify symptom urgency into discrete
categories, and generate medically contextualized advice are all capabilities that
emerge from the supervised instruction fine-tuning stage of the model's training. When
MediScan's symptom service constructs its prompt and requests a structured
assessment, it is leveraging the model's learned ability to map structured natural
language inputs to structured natural language outputs, which is a supervised
generalization capability. The system does not implement any unsupervised
clustering, dimensionality reduction, or generative model training of its own. The pre-
trained, instruction-tuned Mistral model is consumed as an API service, and the
system's AI intelligence is entirely derived from the model's pre-existing supervised
learning.

1.2.3 Mathematics Behind the AI and Model Description
The Mistral model used in MediScan belongs to the family of transformer-based large
language models, whose mathematical foundation is the self-attention mechanism
introduced by Vaswani et al. (2017). The core operation of a transformer layer is the
scaled dot-product attention function, defined as:

                 Attention(Q, K, V) = softmax( QK / dk ) V

where Q represents the query matrix, K the key matrix, V the value matrix, and dk is
the dimensionality of the key vectors used as a scaling factor to prevent the dot
products from becoming too large and causing the softmax function to saturate in
regions of very small gradients. The attention scores determine how much each token
in the sequence attends to every other token, allowing the model to capture long-range
dependencies in the input text.

Multi-head attention extends this by running h parallel attention operations with
different learned projection matrices, allowing the model to attend to information from
different representation subspaces simultaneously:

            MultiHead(Q, K, V) = Concat(head, ..., head) W

where each head = Attention(Q W, K W, V W) with learned weight matrices for
each head. The transformer architecture stacks multiple such attention layers

                                                       13
interleaved with feed-forward networks and layer normalization, building a deep
representation of the input token sequence.
Mistral 7B, the model family underlying MediScan's symptom checker, introduces two
specific architectural improvements over standard transformers: Grouped Query
Attention (GQA) and Sliding Window Attention (SWA). GQA reduces the
computational cost of multi-head attention by sharing key and value projection
matrices across groups of query heads, reducing memory bandwidth requirements
without significant quality loss (Ainslie et al., 2023). SWA restricts each token's
attention to a fixed window of preceding tokens rather than the full sequence, enabling
efficient handling of long contexts while maintaining O(n) complexity in sequence
length (Jiang et al., 2023).
In MediScan's symptom service, the system constructs a structured prompt that
encodes the patient's symptoms, duration, severity, and relief factors as a natural
language input message within the Mistral chat completion format. The model
processes this through its transformer layers, generating output tokens
autoregressively -- each output token is sampled from the probability distribution over
the vocabulary conditioned on all preceding tokens, expressed as:

                       P(x | x, ..., x) = softmax( W h )
where h is the transformer's hidden state at position t and W is the output projection
matrix mapping to vocabulary logits. The system instructs the model to respond only
in valid JSON format, and the service then parses and normalizes the JSON output
through the normalizeAssessment function. When the provider returns an error or
capacity response, the buildFallbackAssessment function applies to a deterministic
rule-based urgency classification as a safety net.

1.2.4 Agent Description
Within MediScan, the AI component operates as a reactive intelligent agent in the
sense defined by Russell and Norvig (2020): an entity that perceives its environment
through inputs and produces actions based on those perceptions. The agent's
environment is the patient's self-reported symptom profile. Its perception is the
structured prompt constructed by the symptom service from the symptom names,
duration value, severity score, and relief factor strings submitted by the patient. Its
action is the generation of a structured clinical assessment containing an urgency
level, a list of possible conditions, care recommendations, over-the-counter options
where appropriate, and a medical disclaimer.
The agent is a goal-based agent: its goal is to produce a clinically conservative,
structured, and actionable triage assessment from the symptom input. It is not an
autonomous agent in the sense of taking actions in the physical world. It does not
access patient medical records, does not interact with external healthcare databases,
and does not make clinical decisions. Its role is strictly advisory and informational: to
assist patients in understanding the potential significance of their symptoms and in
deciding whether to seek self-care, clinic care, urgent care, or emergency escalation
before a formal clinical consultation. The system is explicit about this limitation through
the mandatory disclaimer included in every assessment output.
The agent operates in a single-turn, request-response interaction pattern. Each
symptom analysis request is stateless: the model receives no memory of previous
interactions, and each analysis is conducted independently. This design is intentional
-- it prevents the model from making compound inferences across multiple sessions
that could introduce diagnostic error, and it ensures that every assessment is
grounded solely in the symptom data the patient has explicitly submitted for that
session.

1.6 Academic Question

1.6.1 Detailed Explanation of the Academic Question
The academic question driving this project is: To what extent does AI-assisted
symptom triage improve early healthcare support compared to manual symptom self-
assessment?

This question addresses a gap in outpatient digital healthcare: the period between a
patient noticing symptoms and deciding to seek medical attention. In the absence of
clinical guidance, patients commonly resort to general web searches, which produce
unfiltered results ranging from accurate clinical information to misleading or anxiety-
inducing content. Manual self-assessment tools such as static symptom lists or
condition databases require patients to navigate complex medical terminology without
contextual interpretation of their specific combination of symptoms, duration, and
severity.

AI-assisted triage, as implemented in MediScan, addresses this gap by interpreting
the patient's symptom profile as a whole -- not as a list of individual conditions -- and

                                                       20
generating a contextualized assessment that classifies urgency, suggests possible
conditions, recommends appropriate care pathways, and provides actionable
guidance. The use of a large language model for this purpose leverages NLP
capabilities that general-purpose search engines do not provide: the ability to reason
over the combination of symptoms, to apply conservative clinical framing, and to
generate a coherent, structured, and readable assessment tailored to the specific
input.

The academic question is explored further in Section 2 through a review of relevant
literature on AI in clinical decision support and NLP-based symptom analysis, and in
Section 7 through a critical evaluation of the extent to which MediScan's
implementation delivers the decision support improvements it was designed to
provide.

1.7 Scope and Limitations

The implemented scope of MediScan covers all functionality evidenced by working
backend service logic, API endpoints, and corresponding frontend interface
components. This includes: local and Google OAuth authentication for all three roles;
public verified doctor directory; appointment booking lifecycle with slot validation;
doctor consultation note management; patient record timeline generation; AI-assisted
symptom triage with Mistral integration and rule-based fallback; PDF export of
symptom assessments; care plan publishing, booking, and management; booking
confirmation payment handling; simple medicine inventory tracking; in-app notification
inbox with email integration; automated appointment reminder scheduling; Google
Calendar connect and disconnect; Swagger API documentation; and frontend health
monitoring.

The following limitations exist in the current implementation. No automated test files
were found in the codebase -- no Jest, React Testing Library, or backend integration
tests are present, which represents a significant engineering gap for a system of this
clinical nature. Google Calendar synchronization exists as a service but does not
appear to be invoked from appointment mutations, meaning appointment events are
not automatically created, updated, or deleted in connected doctor calendars.
Authentication defaults include insecure fallback values for the JWT secret and

                                                       21
superadmin setup key that must be overridden in production deployments. File
uploads are handled as base64 JSON payloads rather than multipart streams, which
creates memory pressure for large files. Most admin and listing endpoints do not
implement pagination. No audit log entity records superadmin actions such as user
blocking or verification. Some frontend pages exist in the codebase but are not
exposed through the router, indicating incomplete feature iterations.

2. Literature Review

2.1 Digital Healthcare Platforms and Patient-Centred Systems

The digitization of outpatient healthcare services has been the subject of sustained
academic attention since the early proliferation of electronic health record systems.
Ludwick and Doucette (2009) conducted an extensive review of electronic health
record adoption and found that the most significant barriers to adoption were not
technological but organizational: the fragmentation of clinical workflows across
disconnected systems, and the absence of unified platforms that could serve multiple
stakeholder roles simultaneously. MediScan addresses both barriers directly by
integrating patient-facing, doctor-facing, and administrative functionality within a single
platform with shared data persistence.

Eysenbach (2001) defined eHealth as health services and information delivered or
enhanced through the internet, and identified accessibility, quality, and interactivity as
its core dimensions. MediScan is an eHealth platform in this sense: it is web-based,
provides patient access to verified clinical information and services, and supports
interactive workflows between patients and doctors. The role-based architecture
ensures that each user group receives an interface tailored to their specific needs and
permissions, addressing the quality and relevance dimensions of eHealth as
Eysenbach defines them.

Research on appointment management systems by Marcu et al. (2020) identified
double-booking, lack of real-time availability information, and poor consultation record
continuity as the primary operational pain points in outpatient scheduling. MediScan
addresses all three through the activeSlotKey uniqueness constraint preventing
double-booking, the getDoctorAvailability endpoint providing real-time slot information,
and the getDoctorPatientRecord timeline function maintaining consultation continuity
across appointments.

2.2 AI in Clinical Decision Support and Symptom Triage

The application of artificial intelligence to clinical decision support is one of the most
rapidly evolving areas of health informatics research. Topol (2019) provides a
comprehensive analysis of how deep learning and natural language processing are
transforming medicine, arguing that AI systems can augment clinical decision-making

                                                       23
by processing complex, multi-dimensional patient data at a scale and speed that
exceeds human capacity. MediScan's symptom checker implements a bounded
version of this principle: rather than making clinical diagnoses, it applies NLP-based
reasoning to generate structured triage guidance that helps patients contextualise their
symptoms before seeking care.

Peng et al. (2022) evaluated large language models for medical question answering
and found that transformer-based models, when appropriately prompted, could
produce clinically relevant responses to symptom queries with accuracy comparable
to non-specialist medical reference sources. Their analysis highlighted the importance
of prompt structure in eliciting reliable medical responses -- a finding directly reflected
in MediScan's symptom service, which constructs a carefully structured clinical prompt
specifying the desired output format, conservative safety framing, and JSON response
requirements before submitting the patient's symptom data to the Mistral model.

Jiang et al. (2023) introduced the Mistral 7B model and demonstrated its performance
across a range of reasoning and language understanding benchmarks, showing that
it outperforms larger models from prior generations on several metrics due to its use
of Grouped Query Attention and Sliding Window Attention. For a symptom triage use
case, these architectural improvements are relevant because they enable the model
to efficiently process longer prompts that include detailed symptom context without
degraded performance. The model's instruction-following capability, established
through its fine-tuning process, is what enables MediScan to reliably elicit structured
JSON output from a natural language prompt.

Ouyang et al. (2022) describe the InstructGPT approach of using reinforcement
learning from human feedback to align large language models with human instructions
and preferences. Mistral models trained with similar instruction-following fine-tuning
approaches inherit this alignment property, which is critical for a clinical application
where the model must consistently produce conservative, safety-first language and
refuse to provide diagnostic certainty. MediScan's system prompt explicitly instructs
the model to avoid claiming diagnostic certainty and to recommend professional
consultation, which aligns with the instruction-following behaviour that fine-tuned
models are specifically optimised to exhibit.

2.3 Comparable Systems

2.3.1 Commercial Healthcare Platforms

Practo is a widely used digital health platform in South Asia providing doctor discovery,
appointment booking, and teleconsultation services (Practo, 2025). Compared to
MediScan, Practo operates at commercial scale with thousands of verified doctors,
payment gateway integrations, and mobile applications. However, Practo does not
expose its implementation architecture for academic analysis, and its symptom
assessment features are limited to simple keyword matching rather than LLM-based
natural language triage. MediScan provides a more transparent and educationally
significant artefact as an open, fully custom-built system.

Ada Health is an AI-powered symptom assessment application that uses a
probabilistic symptom model to generate differential diagnoses (Ada, 2025). Ada's
approach is based on Bayesian inference and structured medical ontologies,
contrasting with MediScan's approach of leveraging a general-purpose LLM for free-
form natural language symptom description. Ada's strength is probabilistic precision;
MediScan's strength is natural language flexibility -- patients can describe symptoms
in their own words rather than navigating a constrained structured input tree. Devlin et
al. (2019) note that transformer models trained on large corpora develop strong
contextual understanding of medical language, which may enable MediScan to handle
ambiguous or colloquial symptom descriptions that structured systems would
misclassify or fail to accept.

Zocdoc provides doctor discovery and appointment booking but does not include
symptom assessment functionality (Zocdoc, 2025). MediScan extends beyond
Zocdoc's scope by integrating symptom triage, consultation record management, care
plans, and a notification infrastructure into a single platform.

2.3.2 Academic Prototype Systems

Ahmed et al. (2021) present a web-based telemedicine system for rural healthcare in
developing economies that combines appointment booking with basic symptom input,
using keyword matching to suggest relevant doctor specialisations. Compared to
MediScan, their system implements a narrower symptom analysis approach --
keyword matching rather than LLM-based NLP -- and does not support consultation

                                                       25
record continuity, document uploads, or care plans. MediScan's integration of AI-
assisted NLP triage with a complete outpatient workflow platform represents a more
comprehensive approach.

Comendador et al. (2020) describe PhilNITS, a web-based health information and
triage system for the Philippines that uses rule-based symptom scoring to classify
urgency. Their rule-based approach provides deterministic and explainable triage
results but cannot handle symptom combinations or contextual nuances that fall
outside the predefined rule set. MediScan implements both approaches: the Mistral
LLM provides contextual, language-aware triage for normal operation, and the rule-
based buildFallbackAssessment function provides deterministic triage as a safety
fallback when the AI provider is unavailable. This hybrid architecture is consistent with
the recommendation of Topol (2019) that AI-augmented clinical systems should
always maintain a non-AI pathway for safety-critical decision points.

2.4 AI Algorithm Performance and Related Research

2.4.1 Research Papers and Algorithm Analysis

The foundational algorithm underlying MediScan's AI component is the transformer
architecture introduced by Vaswani et al. (2017) in the landmark paper Attention Is All
You Need. The transformer replaces the recurrent computation of prior sequence
models with a parallelisable self-attention mechanism, enabling training on large
corpora and inference at significantly greater speed. The mathematical basis of the
attention mechanism, as described in Section 1.2.3, enables the model to capture
semantic relationships between symptom descriptions and clinical concepts
regardless of their distance within the input sequence, which is essential for triage
reasoning that must relate symptom duration, severity, and specific symptom names
to urgency classifications.

Jiang et al. (2023) benchmark Mistral 7B against comparable open-weight models
including LLaMA 2 7B and LLaMA 2 13B on reasoning, reading comprehension, and
language understanding tasks. Their results show that Mistral 7B achieves higher
scores than LLaMA 2 13B on several benchmarks despite having fewer parameters,
attributing this efficiency to the GQA and SWA architectural improvements. For
MediScan's deployment context, this performance advantage translates to lower

                                                       26
latency and lower cost per API call for the symptom checker compared to using a
larger baseline transformer model. Ainslie et al. (2023) demonstrate that GQA reduces
memory bandwidth requirements during inference by a factor equal to the grouping
ratio, which contributes to the model's practical usability in a web application context
where response latency directly affects user experience.

2.4.2 Intelligence Goals and Ideas Behind the AI

The intelligence that MediScan's symptom checker attempts to achieve is
conservative clinical reasoning under uncertainty -- a capability that has been a
central objective of AI in medicine since the earliest expert systems of the 1970s. The
MYCIN expert system (Shortliffe, 1976, as cited in Topol, 2019) demonstrated that
rule-based AI could match specialist performance in narrow clinical domains such as
bacterial infection identification. Modern large language models generalise this
capability across a far broader range of symptom presentations through learned
statistical patterns rather than manually encoded rules.

The specific intelligence goal of MediScan's AI is to replicate the initial triage reasoning
that a competent non-specialist would apply when presented with a patient's symptom
profile: classifying the urgency level, identifying the most plausible categories of
conditions consistent with the symptoms, recommending the appropriate care
pathway, and providing practical immediate guidance -- all while maintaining a
conservative, safety-first posture that avoids overconfidence in any specific diagnosis.
This goal is operationalised through the system prompt structure, which instructs the
model on the output format, the urgency classification schema, and the safety
language requirements.

2.4.3 Algorithm Performance Comparison

A meaningful performance comparison for MediScan's AI component involves
comparing the LLM-based approach against the rule-based fallback approach
implemented within the same system. The rule-based buildFallbackAssessment
function classifies urgency based on a simple severity threshold: a severity score
above a fixed threshold triggers a high urgency classification, otherwise a lower
urgency classification is assigned. This approach is fast, deterministic, and requires

                                                       27
no external API call, but it cannot differentiate between symptom combinations that
share the same severity score while having significantly different clinical implications.
The LLM-based approach, by contrast, considers the combination of symptom names,
their number, duration, severity, and relief factors as a holistic input. A patient
presenting with chest pain, shortness of breath, and left arm numbness would receive
a different urgency classification than a patient presenting with a headache and mild
fatigue, even if both have the same numerical severity score. This combinatorial
reasoning is the core performance advantage of the LLM approach over rule-based
alternatives, and is consistent with the findings of Peng et al. (2022), who
demonstrated that LLM-based medical question answering significantly outperforms
rule-based keyword systems on symptom assessment tasks requiring contextual
reasoning.
The trade-off is determinism and explainability. The rule-based fallback always
produces the same output for the same input, which is auditable and predictable. The
LLM may produce subtly different outputs for the same input across different sessions
due to the probabilistic nature of token sampling. MediScan mitigates this through a
fixed temperature setting in the API call (temperature 0.3, set to reduce randomness)
and through the normaliseAssessment function, which maps the model's output to a
standardised structure regardless of minor wording variations.

3. Project Methodology

3.1 Methodology Selection

The development methodology for MediScan was selected based on the project's
context: a single developer building a multi-module healthcare web application with an
AI integration component, where the full implementation details of complex modules
such as the symptom triage pipeline, appointment state machine, and care plan
workflow could only be determined through iterative implementation rather than
complete upfront specification.

Plan-driven approaches such as the Waterfall model (Royce, 1970) were considered
and rejected because they require all requirements to be fully specified before
implementation begins, which is impractical for a system where the AI integration
behavior, the appointment rescheduling state logic, and the Google Calendar
synchronization approach all required experimentation and refinement through the act
of building. Agile frameworks were therefore considered, with Scrum selected as the
most appropriate for the reasons described in Section 3.2.

DSDM was considered but rejected due to its formal multi-stakeholder governance
model designed for commercial team environments (Stapleton, 1997). XP was also
considered; its practices of continuous integration and refactoring were informally
followed during development, but the full XP discipline including mandatory test-first
development for all modules was not proportionate to a solo developer project with
twelve phases to deliver (Beck, 1999).

3.2 Justification of Scrum

Scrum was selected because its sprint-based iterative delivery model aligns directly
with the modular architecture of MediScan. Each backend feature module --
authentication, users, symptoms, appointments, care plans, notifications --
represents a discrete, independently deliverable unit of functionality that maps cleanly
to a sprint deliverable. The development approach of implementing each module as a
complete vertical slice before moving to the next is precisely consistent with Scrum's
principle of delivering a potentially shippable increment at the end of each sprint
(Schwaber and Sutherland, 2020).

                                                       29
The modular structure of the codebase also provides evidence of iterative, sprint-
aligned delivery. The backend is organized by feature module under the module's
directory, and the frontend pages are added by role and concern rather than as a
single monolithic build. The presence of partially integrated features such as Google
Calendar sync and unused frontend pages confirms that development proceeded
incrementally, with later sprints extending the system built in earlier ones rather than
redesigning it.
Scrum's emphasis on inspection and adaptation was particularly relevant for the
symptom checker module, which required multiple iterations of prompt engineering to
produce consistently structured JSON output from the Mistral model, and for the
appointment state machine, where edge cases in the rescheduling and cancellation
flows emerged only during implementation and required design refinement.

4. Technologies and Tools Used

4.1 Justification of Technologies

Every technology choice in MediScan was made based on its suitability for a role-
based, modular healthcare web application with AI and external API integrations. This
section documents the key technologies and provides justification for each.

4.2 Backend Technologies

4.2.1 Node.js and Express
Node.js provides the runtime environment for the MediScan backend. Its non-blocking,
event driven by I/O model is well-suited to a healthcare application with multiple
concurrent connections, asynchronous database queries, and external API calls to the
Mistral AI provider and Google services. Express is a minimal, un-opinionated Node.js
framework that provides HTTP routing, middleware chaining, and REST API
construction without imposing a rigid application structure. It was selected over more
opinionated alternatives because it allows the modular feature-based directory
organization used in MediScan without the structural overhead of a framework like
NestJS. Morgan provides development request logging and cookie-parser enables
server-side reading of HTTP Only auth_token cookie.

4.2.2 MongoDB and Mongoose
MongoDB is a document-oriented NoSQL database selected because MediScan's
data model includes several entities with complex embedded subdocuments that are
awkward to normalize into relational tables. The Appointment model contains
embedded medicalDocuments arrays, embedded availability subdocuments, and
flexible consultation fields that vary in completeness across appointments at different
lifecycle stages. MongoDB's flexible document schema accommodates this variability
natively. Mongoose provides schema definition with field-level validation, population
of referenced documents across collections, automatic timestamp management, and
a query builder that integrates cleanly with the service-layer architecture.

                                                       33
4.2.3 JWT and bcryptjs

Authentication uses JSON Web Tokens issued by jsonwebtoken and stored in
HttpOnly cookies via the setAuthCookie utility. The HttpOnly flag prevents client-side
JavaScript from reading the token, mitigating cross-site scripting risks. bcryptjs is used
for password hashing before persistence and for comparison during login,
implementing the adaptive cost-factor approach that provides resistance against
brute-force attacks (Provos and Mazieres, 1999).

4.2.4 Mistral AI Integration

The symptom checker module integrates with the Mistral AI chat completion API
through the native Node.js Fetch API. The service constructs a structured prompt with
the patient symptom data and submits it as a chat completion request to
config.mistralBaseUrl. The model string and API key are configurable through
environment variables, allowing the system to be pointed at either the official Mistral
API or an OpenRouter-compatible endpoint. The use of the Fetch API rather than a
dedicated Mistral SDK keeps the dependency footprint small and aligns with the
system's principle of preferring native web platform APIs over additional libraries.

4.2.5 Google OAuth and Calendar API

Google OAuth is implemented through googleOAuth.service.js, which handles the
OAuth 2.0 authorization code flow for social sign-in. Upon callback, the service creates
or updates a user record with the Google identity and issues an application JWT. The
Google Calendar API integration in googleCalendar.service.js provides doctor
schedule synchronization, allowing appointment events to be created, updated, and
deleted in a connected doctor's Google Calendar. While the sync service exists and is
partially implemented, it is not currently called appointment mutations as noted in the
limitations.

4.2.6 Nodemailer and Swagger

Nodemailer is used in mailer.service.js to send welcome emails and notification emails
over a configurable SMTP connection. Email sending is wrapped in a non-blocking
async pattern so that email failures do not block core transaction completion. Swagger
documentation is generated from JSDoc route annotations by swagger-jsdoc and

                                                       34
served through an interactive UI at /api/docs by swagger-UI-express, providing a live
API reference for development and testing.

4.3 Frontend Technologies

4.3.1 React and React Router
React provides the component-based architecture for the MediScan frontend. Its
unidirectional data flow, hooks-based state management, and Context API are used
throughout for managing authentication state in AuthContext.jsx, patient appointment
state in usePatientAppointments.js, and doctor dashboard state in
useDoctorDashboard.js. React Router v6 provides the public, patient, doctor, and
admin route separation with RoleRoute.jsx and SuperadminRoute.jsx enforcing role-
based access at the frontend level.

4.3.2 Tailwind CSS, Radix UI, and Supporting Libraries
Tailwind CSS 3 is used for utility-first styling across all dashboard pages, public pages,
and modal components. Radix UI provides the accessible dialog primitive used
throughout the application for appointment booking dialogs, care plan forms,
consultation modals, and confirmation dialogs. framer-motion provides the animation
transitions on the symptom checker wizard and homepage components. jsPDF is used
for client-side PDF generation of the symptom assessment report. lucide-react
provides consistent iconography. react-hot-toast provides lightweight feedback
notifications. class-variance-authority, clsx, and tailwind-merge handle Tailwind class
management in reusable components.

4.4 Development Tools

npm workspaces manages the api and client packages within the monorepo, with
concurrently enabling both applications to run simultaneously from a single npm run
dev command. nodemon provides hot-reload for the backend during development.
ESLint is configured on both the backend and frontend for code quality enforcement.
Git provides version control. The Fetch API is used throughout both the backend's
external API calls and the frontend's server communication instead of Axios, keeping
the dependency tree smaller while aligning with native web platform capabilities.

6. Conclusion

6.1 Revisiting Aims, Objectives, and Academic Question

The first aim of the project was to provide a centralized digital healthcare platform for
patient triage, verified doctor discovery, appointment handling, booking confirmation
payment, medicine inventory awareness, and structured follow-up care. This aim has
been fully achieved. MediScan implements all these functions within a single
integrated platform serving three role-based workspaces backed by a shared
MongoDB database. The system is deployable, demonstrable, and fully functional
across all intended roles.

The second aim was to improve coordination between patients, doctors, and
administrators through role-based workflows, AI-assisted symptom analysis,
automated notifications, and persistent medical interaction records. This has also been
fully achieved. The appointment lifecycle, consultation record system, care plan
workflows, and notification infrastructure all deliver measurable coordination
improvements. The AI symptom checker provides a triage capability that helps
patients contextualize their symptoms before seeking clinical attention, directly
addressing the coordination gap between symptom onset and medical consultation.

Reviewing the six objectives: all six have been implemented and evidenced. Patient
registration, authentication, and healthcare access are met by the authentication
module and patient workspace. Doctor appointment management and consultation
recording are met by the appointment module with full clinical note support.
Superadmin governance is met by the user and care plan management modules. AI-
assisted symptom triage with Mistral integration and fallback is met by the symptom
checker module. Care plan workflows are met by the care plan and booking modules.
The notification and email infrastructure covers all required lifecycle events.

The academic question -- to what extent does AI-assisted symptom triage improve
early healthcare decision support compared to manual symptom self-assessment --
is answered affirmatively with supporting evidence. The Mistral-based NLP triage
interprets the patient's symptom combination holistically, producing contextualized
urgency classifications and care pathway guidance that static keyword search cannot

                                                       80
provide. The hybrid architecture with a rule-based fallback ensures that triage support
is always available regardless of AI provider's availability, demonstrating a responsible
approach to deploying AI in a health context.

6.2 Discoveries and Conclusions

The most significant discovery during development was the importance of prompt
engineering in eliciting reliable, structured output from a large language model. The
initial symptom analysis implementation produced inconsistently formatted responses
that the normaliseAssessment function could not reliably parse. Multiple iterations of
the system prompt -- specifying the exact JSON structure, the urgency classification
schema, the safety-first language requirement, and explicit instructions to produce
only valid JSON with no preamble -- were required before the model produced
consistently parse able output. This experience underscores the finding of Peng et al.
(2022) that prompt structure is the primary determinant of LLM output quality in
medical question answering tasks.

A second discovery was the complexity of the appointment state machine. The
combination of pending, confirmed, rejected, rescheduled, cancelled, and completed
states, with different state transition rules for patient-initiated versus doctor-initiated
actions, and different rescheduling logic for confirmed versus pending appointments,
produced a service layer significantly more complex than initially anticipated. This
reinforced the value of the iterative Scrum approach, as several edge cases in the
state logic were only discovered through manual testing and required sprint-level
refinement.

In conclusion, MediScan represents a technically coherent and practically complete
healthcare web artefact that demonstrates the feasibility of integrating AI-assisted NLP
triage with a full outpatient workflow platform within the scope of a final year project.
The system's modular architecture, role-based access control, and hybrid AI-plus-
fallback design reflect a level of engineering maturity appropriate to a clinically
adjacent application.

7. Critical Evaluation

7.1 Self-Reflection on the Final Report

The development and documentation of MediScan produced a system that exceeded
the initial scope in several areas -- particularly in the richness of the appointment state
machine, the depth of the clinical record model, and the sophistication of the symptom
checker prompt engineering -- while falling short in others, notably the absence of
automated tests and the partial Google Calendar integration. Reflecting on the project,
the most effective decision was the vertical-slice development approach:
implementing each module from backend model to frontend page before moving to
the next kept the system continuously demonstrable and prevented the late-stage
integration failures that commonly afflict systems where backend and frontend are
developed separately.

7.2 Findings and Process Evaluation

The Scrum methodology was an effective choice for this project. The modular
codebase structure provides clear evidence of iterative delivery, with each feature area
added as a coherent increment to the existing working system. The adaptation of
Scrum to a solo developer context -- replacing formal ceremonies with personal
milestone reviews at the completion of each module -- provided adequate structure
without unnecessary overhead.

The decision to use MongoDB over a relational database was validated by the
complexity of the Appointment document model, which embeds medicalDocuments
arrays, consultation fields, reschedule and cancel metadata, and reminder state within
a single document. A relational approach would have required many joined tables to
represent the same data, introducing query complexity that MongoDB's document
model avoids. The trade-off is the absence of database-level referential integrity
constraints, which means the service layer must enforce relationship correctness
through application logic rather than database constraints.

The use of the Fetch API throughout both the backend and frontend was a sound
decision that kept the dependency tree small. The only limitation is slightly more

                                                       82
verbose error handling compared to Axios, but this is a minor concern given the
system's scope.

7.3 System Evaluation

The system's strengths include its architectural coherence, the depth of its clinical
record model, the practical completeness of its appointment lifecycle, and the
innovative inclusion of AI-assisted NLP triage with a safety fallback. The role-based
workspace design provides a genuinely differentiated experience for each user type,
and the notification infrastructure provides comprehensive event coverage across all
significant system actions.

The system's weaknesses fall into three categories. The absence of automated tests
is the most serious engineering limitation. The appointment service, symptom service,
and care plan service all contain complex business logic that is currently verified only
through manual testing. The partial Google Calendar integration represents
incomplete feature delivery. The base64 file upload approach is a scalability risk that
would need to be replaced with multipart streaming uploads before the system could
handle a realistic patient document load.

Evaluating MediScan against the academic question, the AI symptom checker delivers
a meaningful improvement over unaided manual self-assessment. The LLM-based
approach produces contextualized, holistic assessments that cannot be replicated by
keyword matching or static symptom lists, and the hybrid fallback architecture
demonstrates responsible AI deployment. The limitation is the inability to validate the
clinical accuracy of the assessments without a formal medical evaluation study, which
is outside the scope of a final year project. Future work should include clinical expert
evaluation of a sample of assessments to measure their accuracy against professional
triage decisions.

7.4 Planning, Management, and Quality of Sources

The twelve-phase development plan reflected the actual development trajectory, with
the symptom checker phase in Phase 8 taking slightly longer than estimated due to
prompt engineering iterations. Academic sources for the literature review were
selected from peer-reviewed journals and conference proceedings published between

                                                       83
2017 and 2025, satisfying the five-to-six-year recency requirement. Vaswani et al.
(2017) is included as a foundational reference for transformer architecture despite
being at the edge of this range, as it is the essential mathematical basis for all
subsequent LLM discussion. Topol (2019), Peng et al. (2022), Jiang et al. (2023),
Ouyang et al. (2022), and Ainslie et al. (2023) are all within the required recency
window.

7.5 Personal Self-Reflection

This project provided the deepest technical learning of my academic program.
Implementing the LLM integration required understanding transformer architecture,
prompt engineering, JSON schema enforcement in language model outputs, and the
design of hybrid AI-plus-rule-based safety architectures -- none of which were
covered in formal coursework. The appointment state machine required reasoning
about concurrent state transitions, conflict detection, and role-dependent business
rules in a way that is representative of real-world enterprise software complexity.
The most important lesson from this project is the critical importance of automated
testing in systems with clinical implications. The manual testing approach was
sufficient for demonstrating correct behavior but would be entirely inadequate in a
production deployment where patient safety depends on the correctness of triage
outputs, appointment state transitions, and consultation record integrity. Future
development of this system must prioritize a comprehensive automated test suite as
its first task.

10.2 System Setup Guide

    1. Install Node.js and npm.
    2. Ensure MongoDB is running locally or provides a remote MONGO_URI.

                     100
    3. Run npm install inside the app directory to install all workspace dependencies.
    4. Create app/api/.env from app/api/.env.example and populate all required

         variables.
    5. Create app/client/.env from app/client/.env.example and set

         REACT_APP_API_BASE_URL.
    6. Run npm run dev from the app directory to start both backend and frontend

         concurrently.
    7. Optionally seed default users with npm run seed:users --workspace api.
    8. Access the application at http://localhost:3000 and API documentation at

         http://localhost:PORT/api/docs.

10.3 Suggested Automated Test Cases

The following test cases represent the highest-priority automated tests for future
implementation:

Authentication Service
    · Should reject registration with a duplicate email and return 400.
    · Should reject login for a blocked user account and return 403.
    · Should reject access to a protected route without a valid JWT cookie and return
         401.

Symptom Service
    · Should return a structured assessment object with urgency, conditions, and
         care tips for a valid payload.
    · Should return the fallback assessment when the AI provider returns a 429-
         capacity error.
    · Should return a 400-validation error for an invalid duration value.

Appointment Service
    · Should reject booking on a past date and return 400.

                                                      101
    · Should reject a duplicate slot booking and return 409.
    · Should prevent patients rescheduling appointments in pending status without a

         request.
Care Plan Service

    · Should reject care plan creation without assigned doctors and return 400.
    · Should reject deletion of a care plan with existing bookings and return 400.
    · Should reject assignment of doctors whose specialization does not match the

         plan specialty.
